# 51.1 Tool representation

## Scope

[DERIVED] A tool representation connects a proposed model action to a particular executable operation, argument language, identity, semantic precondition and observable result. The baseline is an informal function name with a JSON-shaped argument example. The objective is a contract that distinguishes a well-formed request from a meaningful, authorized and successfully realized action. Chapters 10–11 own model architectures and decoding; Chapter 37 owns constrained generation. Here their output becomes a proposal subject to an execution boundary.

[OFFICIAL-DOCUMENTATION] The current interoperability example is MCP revision 2026-07-28. Its tool definition provides an input schema and optional structured-output schema; names are scoped to a server and annotations are hints [R51.1, Tool/Tool Names/Output Schema; R51.2, Tool/ToolAnnotations]. These interfaces are representations, not certificates of business correctness.

## Why this exists

[DERIVED] Consider an illustrative transfer operation accepting account identifiers and an amount. A string can satisfy a schema while identifying an account outside the caller's authority. A positive number can satisfy a bound while exceeding the current balance. A stale quote can have the correct type while referring to a different exchange-rate version. Even perfect JSON generation cannot decide facts absent from its observations or replace enforcement at the state-owning service.

[DERIVED] Conversely, an executable tool may have too little meaning for a model to select it reliably. An identifier without a domain description encourages accidental substitution; an optional field without a documented default conceals behavior. A description that says “updates a record” does not specify whether absent fields are retained, cleared or recomputed. These are consequential semantics because the same generated bytes can have different effects across adapters.

[DERIVED] Representation therefore serves three consumers: the model that proposes an action, the validator that recognizes permitted syntax, and the executor that checks authority and state. They may share metadata but have different trust requirements. Human-readable descriptions help the first consumer; machine-enforced predicates govern the latter two. A model's confidence belongs to neither authorization nor state evidence.

## Intuition

[DERIVED] A function schema describes a language of candidate calls. A semantic precondition describes the states in which a member of that language is meaningful. Authorization describes which principal may cause which transition. A postcondition describes what must become true if execution is reported successful. Keeping these predicates separate makes failures diagnosable: malformed input, missing information, forbidden operation, stale state and failed execution require different recovery.

[DERIVED] Capability has two relevant senses that must be named. A protocol capability advertises supported functionality. A security capability may be an unforgeable authority-bearing object in a system designed that way. A discoverable tool or an ordinary resource identifier does not acquire the latter meaning merely because it appears in context. Explicitly naming the sense avoids silently promoting descriptive metadata into privilege.

## Formulation

[DERIVED] Let an application tool contract be
$$
\mathfrak t=(\iota,v,\mathcal J_{\rm in},\mathcal J_{\rm out},
P,A,\mathcal F,Q,\mathcal E,\mathcal B).

$$
*(Eq. 51.1)*
Here $\iota$ is a server-qualified operation identity, $v$ its contract revision, $\mathcal J$ the accepted input/output JSON languages, $P(s,a)$ a semantic precondition on authoritative state $s$ and arguments $a$, $A(p,s,a)$ the authorization predicate for verified principal $p$, $\mathcal F$ the allowed state-transition relation, $Q$ a postcondition, $\mathcal E$ the error/status contract and $\mathcal B$ resource and lifetime bounds. This is a book contract, not an assertion that MCP serializes every component.

[MATHEMATICALLY-DERIVED] Valid execution requires a conjunction:
$$
a\in\mathcal J_{\rm in}\ \land\ P(s,a)\ \land\ A(p,s,a),\qquad
(s',r)\in\mathcal F(s,a)\ \land\ r\in\mathcal J_{\rm out}\ \land\ Q(s,s',a,r),\quad \gamma_{\rm in}=\mathbf1[a\in\mathcal J_{\rm in}]\mathbf1[P(s,a)]\mathbf1[A(p,s,a)].

$$
*(Eq. 51.2)*
Satisfying one factor does not imply another. A counterexample is an unauthorized but syntactically valid account identifier. An uncertain precondition is not true; the controller must obtain authoritative evidence or decline the transition.

[DERIVED] An argument should retain provenance $\pi(a_j)$: user-supplied, trusted lookup, deterministic transformation, default or model inference. The representation needs units, identifier namespace, time zone, null/absence semantics, bounds and required relationships. For an illustrative date interval, individual dates can be valid while end precedes start; for a monetary operation, binary floating-point and currency omission can create a numerically representable but semantically ambiguous request.

## Mechanism

### Methodology

[DERIVED] First fix operation identity independently of its display name. Bind server identity, contract revision and operation identifier in the registry. Two servers exposing “search” must remain distinct even when descriptions resemble one another. Next compile the schema under a named dialect and bounded reference-resolution policy. Required fields, additional fields, unions, numeric bounds and string lengths affect the recognized language; documentation examples alone do not specify it.

[OFFICIAL-DOCUMENTATION] JSON Schema 2020-12 distinguishes assertions and annotations, including a configurable treatment of format [R51.3, §§6–7]. A declared format is therefore not a universal guarantee that every validator enforces a domain-specific date or email policy. MCP defaults to that dialect where none is supplied and requires object-shaped tool arguments [R51.1, Tool; R51.2, Tool].

[DERIVED] Then describe preconditions, output meaning and error classes. A result must distinguish “not found” from “permission denied” where disclosure policy allows, “operation accepted” from “operation completed”, and “empty successful search” from “search failed”. For mutating operations, include expected state version, deduplication semantics and reconciliation method if the backing service supports them. Unsupported guarantees remain absent rather than fabricated in the wrapper.

[DERIVED] Finally bind enforcement to execution. Schema validation happens before dispatch; authoritative preconditions and authorization happen where state is owned, with an atomic version check when concurrent change matters. Output validation happens before application interpretation. Trusted normalization can change representation only under a documented mapping; silently coercing a string to a number or replacing an unknown identifier can change intent.

[DERIVED] **Cost.** For bounded nonrecursive fields and fixed validators, a single traversal can scale with serialized input size; arbitrary schema composition, regular expressions and external references defeat an unconditional linear bound. Record validation time, compilation/cache memory, maximum bytes/depth, reference-fetch policy and output limits. Tool descriptions also consume model context: catalog-token cost is distinct from execution cost.

[PAPER-REPORTED] Toolformer samples candidate API insertions, executes them, keeps calls whose results reduce weighted future-token loss against no-call and call-without-result alternatives, and fine-tunes on augmented text [R51.4, §2]. Its filter is $\Delta=\min(\ell_{\rm none},\ell_{\rm call-only})-\ell_{\rm call+result}\ge\tau_f$, where each $\ell$ is a weighted negative log-likelihood of future tokens. Its learning target rewards predictive usefulness. It does not establish semantic preconditions or authorization.

[DERIVED] That distinction explains an objective mismatch: a response can improve token prediction while violating an application's policy. A model optimized for helpful continuations still needs Eq. 51.2 enforced externally. Training and runtime contracts complement one another because neither contains the other's evidence by default.

## Algorithm

> **Algorithm 51.1 — Bounded contract acceptance.** [DERIVED] Inputs are finite registry $\mathcal T$, proposed $(\iota,v,a)$ with per-argument provenance $\pi$, verified principal $p$, deadline, byte/depth bounds and authoritative state interface. Output is an accepted proposal or typed rejection; this procedure does not itself commit a mutation.

$$
\begin{aligned}
1.&\quad z\leftarrow\operatorname{LookupExact}(\mathcal T,\iota,v);
\quad \operatorname{KnownIdentityWrongRevision}(\mathcal T,\iota,v)\Rightarrow\operatorname{Return}(\mathrm{stale});\quad z=\varnothing\Rightarrow\operatorname{Reject}(\mathrm{unknown});\,\operatorname{Stop}.\\
2.&\quad \operatorname{OverBudget}(a)\Rightarrow
\operatorname{Reject}(\mathrm{bounds});\,\operatorname{Stop}.\\
3.&\quad a\notin\mathcal J_{\rm in}\Rightarrow
\operatorname{Reject}(\mathrm{schema});\,\operatorname{Stop}.\\
4.&\quad \operatorname{RequiredProvenanceUnknown}(\pi)\Rightarrow\operatorname{Return}(\mathrm{needs\ information});\quad e\leftarrow\operatorname{ObtainBoundedAuthoritativeEvidence};
\quad \operatorname{Missing}(e)\Rightarrow\operatorname{Return}(\mathrm{needs\ information}).\\
5.&\quad \neg P(e,a)\Rightarrow\operatorname{Reject}(\mathrm{precondition});\,\operatorname{Stop};
\quad \neg A(p,e,a)\Rightarrow\operatorname{Reject}(\mathrm{authority});\,\operatorname{Stop}.\\
6.&\quad \operatorname{Return}(\iota,v,a,\pi,e,\mathrm{accepted\ proposal}).
\end{aligned}
$$

[DERIVED] Invariants are exact identity, unchanged intended arguments, bounded parser/evidence work and no effect before all required gates. Missing required provenance/evidence, silent type coercion and deadline exhaustion reject or return needs-information explicitly. The executor must recheck state-sensitive predicates at commit: acceptance here cannot freeze the external world.

## Implementation

[OFFICIAL-DOCUMENTATION] Static inspection of MCP schema commit 5ea996028df322ce97d1c906731cf8c05a6e268e finds distinct Tool, ToolAnnotations and CallToolRequestParams definitions [R51.2]. These establish wire-level fields and hints; no client/server was executed. Structured output is server-produced data and remains distinct from schema-constrained model generation [R51.1, Structured Content].

[DERIVED] An adapter should retain both raw and validated representations with secret-aware logging. Generated programming-language types are useful developer interfaces, but do not replace runtime validation of network bytes. Treat output strings, embedded resources and links as data with provenance. A schema that accepts an arbitrary string accepts malicious instructions as well as benign prose; it does not assign instructional authority.

[DERIVED] Define the handling of unsupported schema keywords before advertising strict validation. Reject an unsupported contract or explicitly narrow its supported domain. Partial enforcement described as complete validation produces a false safety boundary. Version the normalized schema together with adapter behavior so a cached grammar cannot validate against yesterday's required fields while today's executor applies different defaults.

## Experimental design

### Reported experiments

[PAPER-REPORTED] Toolformer's historical experiments train GPT-J 6.7B on API-augmented CCNet text and compare tool-enabled, disabled and further-pretrained baselines on language, arithmetic, QA and temporal tasks [R51.4, §4]. These assess useful learned calling in that regime; they do not measure current protocol compliance or production mutation safety.

[PAPER-REPORTED] τ-bench instead evaluates database outcomes and required communicated information in retail/airline conversations [P43, §§3–5]. Its separation of API checks from policy requirements makes it relevant evidence that function-call availability and task correctness are different. The detailed repeated-trial interpretation belongs to §51.4.

## Observations

**What the paper claims.** [OFFICIAL-DOCUMENTATION] Schemas define callable structures [R51.1–R51.3]. [PAPER-REPORTED] Toolformer learns predictively useful calls [R51.4, §2].

**What the evidence shows.** [OFFICIAL-DOCUMENTATION] The inspected fields define accepted structures [R51.2]. [PAPER-REPORTED] Historical studies evaluate predictive or environment outcomes under their own protocols [R51.4–P43].

**What we infer.** [DERIVED] Enforcing syntax can isolate one failure class and improve diagnostics.

**What remains unknown.** [UNVERIFIED] No inspected result proves that an arbitrary valid call is authorized, policy-compliant or safe on a live service.

## Failure modes

[DERIVED] Name collision appears as a correct-looking call sent to the wrong server; detect it through qualified identity and registry revision. Unit/default mismatch appears as valid bytes with unexpected magnitude or clearing behavior; retain normalized arguments and explicit defaults. Stale schema appears as rejected or misinterpreted calls after updates; invalidate caches by version. Time-of-check drift appears when a previously valid precondition fails at commit; use authoritative version checks rather than repeated model reassurance.

[DERIVED] A broad “execute command” schema has little semantic containment even if parsing is perfect. Narrow typed operations reduce ambiguity only when their implementations enforce the declared domain. A wrapper around unrestricted execution does not inherit safety from having fewer JSON keys.

## Siblings

[DERIVED] Text-only API encodings are flexible but require parsing and preserve fewer machine-checkable distinctions. Typed RPC/OpenAPI-style adapters expose different interface contracts; no protocol changes the underlying business authorization. Chapter 37 covers constrained decoding, Chapter 50 context provenance, and §51.3 transport/version mechanics. Compare representations at equal supported operations and enforcement, rather than treating schema size as task capability.

## Extensions

### Improvements

[DERIVED] A stronger representation adds stable identity, provenance and semantic/error contracts to structural schemas. The changed mechanism is explicit information available to validators and executors; no measured success increase is asserted here. Toolformer supplies a historical learned-calling route, while the 2026 MCP contract supplies current interoperability fields. They solve different parts of the pipeline.

[DERIVED] Unresolved research concerns learning calibrated precondition uncertainty from partial observations without turning model estimates into authority. Evidence would require tasks with controlled hidden-state ambiguity, independent state checks and explicit abstention costs; syntactic accuracy alone cannot settle it.

## Limitations

[DERIVED] Full business semantics rarely fit a finite static schema. Authority changes, external state and nondeterministic services constrain any formal contract. The book predicates specify obligations, not a universal verification algorithm. Schema expressiveness can itself create denial-of-service or unsupported-feature risks. No empirical claim of validator completeness is made.

## Reproducibility

[UNVERIFIED] Execution requires pinned schema compiler, keyword support, remote-reference policy, adapter identity, fixtures, principal mapping and actual backing-state transitions. Current evidence is source inspection and derivation. Proposed malformed/semantic/authority tests are in verification.md, separate from source-reported studies.
