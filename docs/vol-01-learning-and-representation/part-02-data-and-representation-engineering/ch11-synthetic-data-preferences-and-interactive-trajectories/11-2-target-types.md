# 11.2 Target types

## Scope

Objective: give a typed taxonomy of the things a synthetic (or human) data pipeline can produce as *training targets* — instructions, responses, rationales, demonstrations, preferences, reward labels, verifier labels, and tool trajectories — and bind each type to the training role of [Appendix C](../../../appendices/appendix-c-dataset-atlas-and-training-role-taxonomy.md) that consumes it, the loss structure that reads it, and the fields it must carry. Baseline: a single "instruction dataset" JSONL whose rows are used interchangeably for SFT, preference training, and reward modelling. Success: for any row in a corpus, a reader can name its type, the objective family that can legally consume it, and the field whose absence would make that consumption invalid. Boundaries: the objectives themselves (SFT loss and masking, preference likelihoods, reward-model losses, RLVR rewards) are owned by Chapters 31–35; this section owns the *record types* and their conversions.

## Why this exists

What failed before was type confusion in post-training data. A preference pair whose "rejected" side is a perfectly good answer was used as if "rejected" meant "bad"; a rationale whose final answer was correct was treated as a correct rationale; a tool trajectory with a tool error in the middle was trained as a demonstration of the whole; an instruction generated by a model was fed to a reward model as if it carried a quality label. TRL's documentation carries the trace of this history in its warning that "the `"chosen"` and `"rejected"` completions in a preference dataset can be both good or bad", so that before converting to an unpaired type one must "ensure that all `"chosen"` completions can be labeled as good and all `"rejected"` completions as bad" — "by checking absolute rating of each completion, e.g. from a reward model" (OFFICIAL-DOCUMENTATION · R11.11). The bottleneck that appeared was that every post-training algorithm reads a *different* structure: SFT reads a masked sequence, DPO reads a pair, KTO reads a labelled single, PRM training reads step labels, GRPO reads prompts only and produces its own completions (OFFICIAL-DOCUMENTATION · R11.11, the trainer-to-type table). The constraint that became dominant is that the *semantics of a label* — whether a "1" means "a human preferred it", "a test passed", "a model judged it acceptable", or "the final token matched" — is not recoverable from the column name. What changed is that recipes now report types explicitly: Tulu 3 separates an SFT mixture (939,344 prompts), a preference set (354,192 instances built by generating completions "from Tülu 3-SFT and other models" and obtaining "preference labels through their pairwise comparisons"), and a verifiable-reward set of prompts with executable checks (PAPER-REPORTED · P29); DeepSeek-R1 separates cold-start long-CoT data, rejection-sampled reasoning data (≈600k), and non-reasoning data (≈200k) with different provenance for each (PAPER-REPORTED · P26). The taxonomy below is the type system those reports imply.

## Intuition

Physically, a target type is the shape of the tensor that reaches a loss, plus the mask that decides which positions contribute. An SFT record becomes one token sequence and a binary mask; a preference record becomes two sequences sharing a prefix and a single comparison; a reward-label record becomes a sequence and a scalar; a verifier-label record becomes a sequence and a bit *with the evidence that produced the bit*; a rationale becomes a sequence in which an intermediate span and a final span have different epistemic status; a trajectory becomes an alternating sequence of policy-produced and environment-produced spans in which only the former are trainable. Every "conversion" between types either discards information (pair → single loses the comparison; rationale → answer loses the intermediate span) or *invents* it (single → pair requires a second sample; SFT → preference requires a comparison that nobody made). The cost of getting a type wrong is not a crash; it is a silently mis-specified objective, which is why the taxonomy is enforced at the record level and not at the trainer.

## Formulation

Let a *target record* be a typed tuple with a header shared by all types:

$$
\rho = \big(\text{type},\; x,\; \text{payload}_{\text{type}},\; \text{label\_semantics},\; \text{provenance}\big)
$$
*(Eq. 11.4)* where type ∈ {INSTR, RESP, RAT, DEMO, PREF, RWD, VER, TRAJ}, x = the prompt or context (conversation prefix, task specification, or environment initial observation), payload_type = the type-specific fields of Table 11.1, label_semantics = a controlled vocabulary entry naming *who or what* produced any label and *what it asserts*, provenance = the §11.1 record (for synthetic rows) or the §7.5 record (for human rows).

*Table 11.1 — Target-type taxonomy.* (DERIVED from the Appendix C role table and the TRL type table; the vocabulary column is the book's proposal.)

> **Definition — target type.** The member of {INSTR, RESP, RAT, DEMO, PREF, RWD, VER, TRAJ} that a training record belongs to, determined by its payload fields and the objective family that may consume it, and carried explicitly in the record rather than inferred from column names.

> **Definition — label semantics.** The controlled-vocabulary entry on a record that states the *producer* of any label (human, model judge, executor, matcher, reward model, environment) and the *proposition* the label asserts (preferred-over, correct-by-test, acceptable-by-rubric, matched-reference), such that two records with the same column layout but different semantics are not merged.

> **Assumption.** A record's type is fixed at creation and conversions produce *new* records with lineage pointers · *sensitivity:* if conversions overwrite in place, the label_semantics of the original is lost and the warning of R11.11 becomes unenforceable.

Conversions between types are partial functions; Table 11.2 lists which are information-preserving (MATHEMATICALLY-DERIVED from the field lists):

| From → To | Preserving? | What is discarded or invented |
|---|---|---|
| PREF → RESP (keep chosen) | discards | the comparison; `chosen` becomes a demonstration only if its absolute quality is known |
| PREF → RWD (unpair) | invents | a per-item absolute label from a relative one; legal only with an absolute rating (R11.11's warning) |
| RAT → RESP (drop rationale) | discards | the intermediate span; the answer's `checked_by` survives |
| VER → RESP (keep pass) | discards | the verdict evidence; the resulting RESP must carry `rejection_sampled:V` |
| RESP × RESP → PREF | invents | a comparison; requires a rater and produces `ai_pairwise` or `human_pairwise` |
| TRAJ → DEMO | discards | terminal outcome, censoring, policy version; produces a demonstration only if the outcome was success |
| VER (step-wise) → VER (outcome) | discards | per-step labels; TRL's stepwise → unpaired conversion uses logical AND over steps (OFFICIAL-DOCUMENTATION · R11.11) |

*Table 11.2 — Conversion lattice.*

## Mechanism

**Instructions.** An instruction record is a prompt with no target. Self-Instruct's pipeline generates instructions first, then classifies each as a classification task or not, then generates instances "input-first" or "output-first" depending on that class (PAPER-REPORTED · R11.1); the separation of instruction generation from instance generation is exactly the INSTR/RESP split. Tulu 3's persona-conditioned prompts for math, code, and precise instruction following are INSTR records with `persona_conditioned` semantics whose *solutions* were generated in a second step by a possibly different teacher (PAPER-REPORTED · P29), so their RESP rows carry a different G. Cost line: an INSTR record costs one teacher call for the prompt text; its later cost is multiplied by however many RESP, PREF, or TRAJ rows are hung on it.

**Responses.** A RESP row is the SFT unit. Its consuming loss is Eq. N.2 with a mask over the prompt; the mask policy (`loss_mask`) is part of the payload because "train on the whole conversation" and "train on the last assistant turn" are different datasets with identical text. Llama 2's finding that "a total of 27,540 annotations" of high quality sufficed — "tens of thousands was enough to achieve a high-quality result" — is a statement about RESP rows with `human_demonstration` semantics (PAPER-REPORTED · R11.5), and cannot be transferred to RESP rows with `teacher_sample` semantics without the §11.3 gate. Cost line: one decode per response; the SFT consumption cost is ≈ 6N tokens FLOPs per trained token per epoch (Chapter 19).

**Rationales.** A RAT row separates the reasoning span from the answer span because their evidential status differs: the answer can be checked, the rationale usually cannot. STaR's construction makes this explicit — it keeps a rationale only if "the generated answers" are correct, and for failures produces a *rationalization* by giving "the correct answer" as a hint and generating the rationale backwards (PAPER-REPORTED · R11.4). The two provenances (`answer_verified:match` versus `rationalized:hint_given`) are different label semantics and STaR itself tracks them (its GSM8K table reports "28.7% of the dataset (with 0.5% from rationalization)"; PAPER-REPORTED · R11.4). R1's reasoning data add a third semantics: samples judged by "a generative reward model by feeding the ground-truth and model predictions into DeepSeek-V3 for judgment" are `model_judge`-labelled, not execution-verified (PAPER-REPORTED · P26). Cost line: rationale rows are long (R1 filtered out "long paragraphs" for readability, PAPER-REPORTED · P26); their decode cost dominates, and the *answer-only* verification cost is small by comparison.

**Demonstrations.** A DEMO row is a multi-turn record with per-turn trainability. TRL's conversational format carries `role`/`content` messages and, for tool use, a `tools` column holding JSON schemas and `tool_calls`/`tool` messages (OFFICIAL-DOCUMENTATION · R11.11). The per-turn `trainable` bit is the book's field: verl's multi-turn documentation states that "only tokens generated by the assistant are included in the loss mask", computed by a delta-tokenisation strategy that compares templates before and after each message (OFFICIAL-DOCUMENTATION · R11.13). A DEMO row generated with a simulated user (τ-bench-style, [§11.5](11-5-interactive-collection.md)) carries *two* generators — the user simulator and the policy — and its `label_semantics` must name both. Cost line: multi-turn rows re-tokenise the growing prefix per turn unless packed ([§12.4](../ch12-scalable-data-infrastructure-and-reproducible-ingestion/12-4-packing-and-masks.md)); the training cost is over all tokens in the sequence, but the gradient signal comes only from trainable turns.

**Preferences.** A PREF row is a comparison, not two labels. Constitutional AI produces AI preferences by generating "a pair of responses to each prompt", formulating "each prompt and pair into a multiple choice question, where we ask which response is best according to a constitutional principle" (PAPER-REPORTED · P22); UltraFeedback instead scores single completions on several aspects with GPT-4 and binarises (PAPER-REPORTED · R11.10, "over 1 million GPT-4 feedback for 250k user-assistant conversations"), which is an RWD → PREF conversion and inherits the caveat of Table 11.2. Llama 3's human preferences add a `strength` field ("one of four levels") and an *edit step* that produces a third, edited response better than both (PAPER-REPORTED · R11.6) — a PREF row whose `chosen` may itself be an edited RESP with `human_edited` semantics. The explicit-prompt layout is what TRL recommends (OFFICIAL-DOCUMENTATION · R11.11). Cost line: a PREF row costs at least two decodes plus one comparison (a rater call or a human judgement); when the rater is a model, the comparison is a further prefill over both responses.

**Reward labels.** An RWD row attaches a scalar. Its semantics must state the scale and the rater; a reward-model score (`reward_model:v_R`) is *derived* from PREF data and must not be fed back as if it were ground truth — [§32.6](../../../vol-02-execution-and-optimization/part-06-post-training-and-reinforcement-learning/ch32-preferences-reward-models-verifiers-and-oversight/32-6-reward-exploitation.md) owns the failure. Llama 3's quality scoring ("both reward model and Llama-based signals", top quartile retained) is an RWD-labelled *selection*, not a training target (PAPER-REPORTED · R11.6). Cost line: one rater forward pass per row.

**Verifier labels.** A VER row is the strict form: a verdict plus the *evidence* that produced it. SWE-bench's `FAIL_TO_PASS` and `PASS_TO_PASS` test lists are the evidence fields for a code patch (PAPER-REPORTED · P42; the harness fields are documented in the repository, OFFICIAL-DOCUMENTATION · R11.18); τ-bench's reward `r = r_action × r_output ∈ {0,1}` compares the final database state to an annotated goal state and the required outputs (PAPER-REPORTED · P43). Tulu 3's RLVR prompts carry verifiable functions for GSM8K, MATH, and IFEval-style constraints (PAPER-REPORTED · P29). The verdict vocabulary includes `error` and `timeout` because an execution that did not complete is not a `fail` — the distinction feeds §11.5's censoring field. Cost line: execution verification costs a sandbox run per row (container start, test runtime), which for repository-level tasks can exceed the generation cost of the row; symbolic matching is near-free; a model judge costs a prefill over the completion.

**Tool trajectories.** A TRAJ row is the object of §11.5; here it is placed in the lattice. Its distinguishing property is that environment-produced spans are *observations*, never targets, and that its terminal outcome is a VER-style verdict over the *final state*, not over the text. Llama 3 reports that for code it generated "unit test generation and execution" feedback in containers and used it to filter and to trigger self-correction (PAPER-REPORTED · R11.6) — a TRAJ-producing loop whose accepted rows are then converted to RESP or DEMO rows (Table 11.2, with the outcome retained in semantics). Cost line: a trajectory costs its policy decodes plus every environment step; environment cost per step is workload-specific and NOT-DISCLOSED here.

## Algorithm

```text
Algorithm 11.2 — Target-record validation and typed conversion
INPUT   a stream of candidate records with declared type; the field contract of Table 11.1;
        a requested output type; an optional absolute-rating source R_abs
OUTPUT  validated records of the requested type, each with lineage to its source record
STATE   rejection log keyed by (record_id, missing_field | illegal_conversion)
INVARIANT  no emitted record lacks a label_semantics entry; every conversion that Table 11.2
           marks "invents" has its invented field's producer recorded
1  For each record ρ: check that payload fields required by ρ.type are present; else log and drop.
2  Check that ρ.label_semantics is in the vocabulary for ρ.type; else log and drop.
3  If ρ.type = requested type: emit ρ unchanged.
4  Else look up (ρ.type → requested) in Table 11.2:
5     if absent: log illegal_conversion and drop.
6     if "discards": emit ρ' with the surviving fields, lineage.parent = ρ.id,
         label_semantics inherited plus "converted_from:ρ.type".
7     if "invents": require the inventing producer (R_abs for PREF→RWD; a rater for
         RESP×RESP→PREF); call it; emit ρ' with the producer named in label_semantics.
8  Emit the rejection log with counts per reason.
```

DERIVED — complexity: O(number of records) field checks plus O(number of invented labels) producer calls; the producer calls dominate cost when a model rater is used (one prefill over the payload per invented label). Termination: the stream is finite. The rejection log is an input to §11.6's accounting of useful samples per cost.

## Implementation

The types map onto reference-stack data contracts. Hugging Face TRL (#29, *Post-training / RL*) documents the *language modeling*, *prompt-only*, *prompt-completion*, *preference*, *unpaired preference*, and *stepwise supervision* types with exact column names (`text`/`messages`; `prompt`; `prompt`+`completion`; `prompt`+`chosen`+`rejected`; `prompt`+`completion`+`label`; `prompt`+`completions`+`labels`), the *standard* versus *conversational* format axis, a `tools` column of JSON schemas generated by `transformers.utils.get_json_schema`, and a table binding each trainer to its expected type (OFFICIAL-DOCUMENTATION · R11.11, v1.13.0). The correspondence is: INSTR ↔ prompt-only; RESP and RAT ↔ prompt-completion (RAT with the rationale inside the completion, which is why RAT needs an out-of-band `answer` span); DEMO ↔ conversational language-modeling with `tools`; PREF ↔ preference; RWD ↔ unpaired preference when binarised (a loss of scale information that must be recorded); VER (step-wise) ↔ stepwise supervision. TRAJ has no TRL type; verl (#37, *Post-training / RL*) produces it as rollout output with per-token loss masks that exclude tool-response tokens (OFFICIAL-DOCUMENTATION · R11.13), and OpenRLHF (#36, *Post-training / RL*) documents a prompt dataset keyed by `--data.input_key` with chat-template application (OFFICIAL-DOCUMENTATION · R11.14). Hugging Face Transformers (#26, *Model definition / adaptation*) owns the chat-template rendering that turns DEMO rows into token sequences; template parity is [§10.4](../ch10-tokenization-serialization-and-interface-correctness/10-4-conversation-serialization.md)'s problem and the tool-call serialisation is [§10.5](../ch10-tokenization-serialization-and-interface-correctness/10-5-tool-and-multimodal-interfaces.md)'s.

```text
Tensor trace (RESP row → SFT batch)
prompt text + completion text → chat template → [T] token ids
[T] ids → shift → inputs [T−1], targets [T−1]
loss_mask policy → m_t ∈ {0,1}^[T−1]   (prompt positions 0; assistant positions 1)
[B, T−1] × mask → Eq. N.2 token-mean over Σ m_t
```

The provenance and `label_semantics` columns are carried alongside and dropped by the trainer's column filter; they must survive in the dataset artifact, not in the batch.

## Experimental design

### Experiment 11.2 — Does label semantics matter at equal column layout?

- **Hypothesis:** two PREF sets with identical layout but different semantics (`human_pairwise` versus `ai_pairwise` from one judge) train reward models whose rankings disagree on a held-out human-labelled set more than seed variance explains.
- **Setup:** same prompts, same candidate responses; labels from (a) human raters under a rubric, (b) one model judge with the same rubric; train one reward model per set, r ≥ 3 seeds.
- **Independent variables:** label producer.
- **Controlled variables:** prompts, responses, reward-model architecture, recipe, held-out set (human-labelled, disjoint prompts).
- **Dataset/workload:** general-assistant prompts; ≥ 10k pairs per arm.
- **Hardware:** one accelerator class; hours logged.
- **Metrics:** held-out pairwise accuracy; agreement between the two reward models (Cohen's κ over held-out pairs); §6.4 intervals.
- **Baselines:** seed-to-seed κ within each arm.
- **Expected result:** cross-arm κ below within-arm κ by more than the interval width → semantics is a material field; otherwise the two producers are interchangeable *for this rubric and judge*.
- **Ablation:** binarise (a)'s ratings through an absolute score to emulate RWD → PREF and measure the loss.
- **Interpretation:** a material gap justifies refusing to merge sets with different semantics.
- **Threats to validity:** the human held-out set shares the rubric with arm (a); judge choice.

Proposal only; no run was executed.

## Observations

**What the paper claims.** P29 claims that separately curated SFT, preference, and verifiable-reward sets, each with reported sizes and sources, yield a reproducible open recipe. P26 claims that ≈800k samples of mixed reasoning and non-reasoning types trained by SFT transfer reasoning behaviour to smaller models. P22 claims that AI-generated pairwise preferences, guided by principles, can replace human harmlessness labels. R11.11 documents the types TRL consumes.

**What the evidence shows.** The trainer-to-type table of R11.11 is documentation of an interface, not of an outcome. P29's separation of types is reported; whether mixing types (e.g. training SFT on chosen sides of the preference set) would have changed its results is not reported. P22's AI-preference claim is supported by its own crowdworker Elo comparisons and has no independent reproduction inspected here.

**What we infer.** DERIVED: Table 11.2's lattice follows from the field lists — the "invents" cells identify the exact points where a pipeline manufactures a label, which is where audits should look. ASSUMED: the eight-type vocabulary is complete for text and tool data; embodied action records (Chapter 60) may need a ninth.

**What remains unknown.** The `strength` distribution of Llama 3's preferences and the rater population are NOT-DISCLOSED. How many of R1's 600k reasoning rows were judged by DeepSeek-V3 versus checked by rule is NOT-DISCLOSED. The loss-mask policy used for R1's SFT (rationale + answer, or answer only) is NOT-DISCLOSED in the pages inspected.

## Failure modes

> **Failure mode — Rejected-as-bad.** *Symptom:* a KTO/unpaired run degrades on prompts where both candidates were good. *Cause:* PREF → RWD conversion without absolute ratings. *Detection:* fraction of `rejected` completions with high absolute score. *Mitigation:* Algorithm 11.2 line 7; R11.11's warning.

> **Failure mode — Rationale trusted by answer.** *Symptom:* the student learns confident but invalid intermediate steps. *Cause:* RAT rows accepted on `answer_verified:match` alone. *Detection:* step-wise audit of a sample; disagreement between answer-match and a process check (§11.3). *Mitigation:* record `checked_by`; sample-audit rationalised rows separately.

> **Failure mode — Environment span trained.** *Symptom:* the policy emits tool outputs instead of tool calls. *Cause:* TRAJ → DEMO conversion with `trainable` bits missing. *Detection:* loss-mask coverage of `tool` role tokens > 0. *Mitigation:* delta-tokenisation masks (R11.13); §10.5 parity checks.

> **Failure mode — Semantics merged across producers.** *Symptom:* a reward model calibrated on human pairs shifts after adding AI pairs. *Cause:* rows merged by column layout. *Detection:* per-semantics accuracy on a human held-out set. *Mitigation:* keep `label_semantics`; Experiment 11.2.

## Extensions

Domain adaptation adds `skill_tag` values and per-domain verifiers to VER. Long-context targets need the `answer` span located by offset, not by string match. Multimodal targets extend `content` to typed lists (R11.11's vision datasets) and VER's evidence to rendered outputs. Agent targets are TRAJ and are developed in §11.5. Embodied action records (Chapter 60) add units, coordinate frames, and control rate to the TRAJ schema; proposal: a ninth type ACT with those fields.

## Limitations

The taxonomy is a design; it has not been validated by an experiment showing that enforcing it improves outcomes (Experiment 11.2 is the proposal). Table 11.2 is exhaustive over the eight types only. The "verifier" versus "model judge" line is drawn by evidence, and some evidence (a proof checker's certificate) is stronger than others (a regex match); the vocabulary records the producer but not a strength ordering. Falsification: if reward models trained on merged human and AI preference sets consistently matched those trained on human-only sets, `label_semantics` would be an audit field rather than a training-relevant one. Decision consequence: a dataset record in this book that lacks a type and semantics is not a training artifact.
